## 写作不是答案的包装

有时，问题并不是不知道答案，而是还没有把问题说清楚。写作能迫使模糊的直觉逐渐变成可以检查的句子。

这篇文章是网站排版和内容发布的**示例内容**，不应被误认为个人经历。真正的文章会在本人确认后替换。

### 从一个具体的问题开始

与其写“学习了某项技术”，不如留下更有用的问题：

- 这项技术解决了什么问题？
- 它的设计选择带来哪些权衡？
- 我能否做一个小实验来验证自己的理解？

问题越具体，下一次回到这份笔记时，就越容易接着往下走。

## 留下可复查的证据

在代码和工具相关的笔记里，记录**输入、观察结果与限制条件**，往往比单独给结论更有价值：

```ts
interface Note {
  question: string;
  observation: string;
  nextStep: string;
}
```

这样，当环境或结论发生变化时，也知道从哪里重新检查。

### 适时收束

不是每一个草稿都需要变成文章。可以先把它放进数字花园，等到有新的例子、资料或实践时再整理。

| 阶段      | 可以做的事               |
| --------- | ------------------------ |
| Seedling  | 记下问题或线索           |
| Growing   | 补上来源和自己的例子     |
| Evergreen | 定期检查结论是否依然有效 |

## 留一点空白

不确定的地方，可以坦然标记为“待验证”。把限制写出来，不会削弱文章，反而能让未来的读者更容易判断它适用在哪里。

下一次学习时，也许可以从一张小卡片开始：问题、来源、例子、下一步。慢慢地，它们会连成一张属于自己的地图。
